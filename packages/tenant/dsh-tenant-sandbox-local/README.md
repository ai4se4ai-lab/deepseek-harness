# @mindportalix/dsh-tenant-sandbox-local

Tenant-scoped fork of `@deepseek-ai/dsh-sandbox-local`, for the single shared DSH container behind the MindPortalix reverse proxy. Registers as `ctx.sandbox`, replacing the upstream provider (see `deploy/tenant-isolation.cordis.patch.yml`, which disables the base `sandbox` row and inserts this one in its place — Cordis id-targeted patches cannot change which plugin package an existing row loads).

The upstream `bwrapProfileArgs`/`landlockProfileArgs` grant a confined command read access to the **entire container filesystem** (`--ro-bind / /` / `readOnly: ['/']`) and write access only to the session's own workspace. That blanket read grant is exactly the cross-tenant read path this package closes: `bwrapProfileArgs(policy, tenantRoot)` / `landlockProfileArgs(policy, tenantRoot)` grant read access to a fixed system allowlist (`/usr`, `/bin`, `/sbin`, `/lib`, plus `/lib64`, `/etc/resolv.conf`, `/etc/hosts`, `/etc/ssl`, `/etc/passwd`, `/etc/nsswitch.conf` where present) and to exactly the calling tenant's own `$DSH_HOME/tenants/<tenantId>` root — never any other tenant's directory, and never the rest of the filesystem.

`TenantSandboxLocalProvider.confine()` resolves `tenantRoot` from `ctx.tenantContext.requireCurrent()` on every call and fails closed: with no tenant identity bound to the calling async chain, it throws instead of falling back to an unconfined or upstream-shaped profile. A `workspace-write` policy whose `workspaceRoot` falls outside the resolved tenant root is refused for the same reason — defense in depth beneath `@mindportalix/dsh-tenant-session-guard`, which is what is supposed to keep `workspaceRoot` inside the tenant root in the first place.

`seatbeltProfileArgs` (macOS) and the Windows ACL rung are unmodified re-exports/copies from upstream: this container is Linux-only, so they are out of scope for this fork.

## Model Experience

This package has no model, token, or KV-cache effect: it is a process-sandbox backend with no system-prompt, tool, or session-log surface.

## Known Limitations and Deferred Work

- **Empirically validated, in the actual shipped image, with a real confined process — see below for exactly what was run and what it proved.** The allowlist and the tenant-scoping logic in this package were exercised end to end: built `docker compose -f docker-compose.yml -f docker-compose.dsh.yml build deepseek-harness` from the outer MindPortalix repo, ran the resulting `mindportalix-dsh:local` image with no special container privileges (no `--privileged`, no added capabilities, no seccomp/apparmor override — the exact profile `docker-compose.dsh.yml` runs with), and inside it drove `TenantSandboxLocalProvider.confine()` directly for two distinct tenant ids, `execFileSync`-ing the returned argv for real.
  - **Backend that actually engages in this deployment: Landlock, not bwrap.** `bwrap` is now installed in the image (see the Dockerfile), but Docker's default seccomp/security profile blocks unprivileged Linux user-namespace creation (`bwrap: No permissions to create new namespace...`), confirmed directly by running `bwrap` by hand inside the container — this is normal, expected Docker behavior, not a bug, and `docker-compose.dsh.yml` grants no extra privileges that would change it. The provider's own fallback chain (`bwrap` → `landlock`) selects Landlock automatically in this environment; `confine()`'s returned `enforcement` reported `'full'`.
  - **Read isolation, proven with a real kernel-level denial, not a coincidental miss:** as tenant A, wrote a file under A's tenant root; as tenant B, ran a Landlock-confined `cat <A's absolute path>` — denied with `cat: /data/tenants/<A>/secret.txt: Permission denied`, and a confined `ls` of A's tenant root similarly denied with `Permission denied` (not `No such file or directory` — proof the kernel is refusing the access, not merely failing to resolve a path).
  - **Write isolation, same proof shape:** tenant A writing inside its own `workspace-write` root succeeded; tenant B attempting to write inside A's tenant root was denied with `Permission denied`.
  - **Ordinary tool operation under the narrowed allowlist, all confirmed working inside the same confined process:** bash builtins (`echo`, `pwd`, `type`), spawning a `node` subprocess, reading `/etc/resolv.conf`/`/etc/passwd`/`/etc/ssl/certs`, and — going further than a static-file check — an actual DNS lookup (`node:dns` resolving a real hostname to an IP) succeeded under confinement.
  - **Fail-closed, confirmed:** calling `confine()` outside any `ctx.tenantContext.run(...)` threw `TenantRequiredError`, exactly as designed — never an unconfined fallback.
  - Caveat on the allowlist specifically: the exercised tool surface (bash builtins, `node`, DNS resolution, reading `/etc/ssl` certs) did not include a live-`DEEPSEEK_API_KEY` HTTPS call or every shipped skill/tool; if a future tool needs a system path outside `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc/resolv.conf`, `/etc/hosts`, `/etc/ssl`, `/etc/passwd`, `/etc/nsswitch.conf`, or the tenant root, it will fail the same way TEST 8/9 above did until this package's `profiles.ts` allowlist is extended.
- **Discovered along the way, fixed, and worth flagging: neither Linux confinement backend was usable in this image before this validation pass**, independent of anything in this fork — `bubblewrap` was absent from the `node:*-bookworm-slim` base and this Dockerfile (now installed; see the Dockerfile's runtime-stage comment), and the Landlock launcher's native binary (`native/landlock-run/packages/linux-*/bin/landlock-run`) is a CI release artifact that was not present in this git checkout at all (its containing directory is git-ignored by design — CI builds it per architecture). The unmodified upstream `@deepseek-ai/dsh-sandbox-local` hits the identical `SANDBOX_UNAVAILABLE` failure in this same image; this is a pre-existing gap in the harness's Linux sandbox story, not something this fork introduced. For this validation pass, the `linux-arm64` binary was built locally with `musl-gcc` (`native/landlock-run/scripts/build.ts`'s exact compile invocation) to match this host's architecture — a local, git-ignored artifact for testing, not a substitute for CI producing and shipping the real release binaries. **Before this deployment is production-ready, confirm CI's `Landlock Run` / `Landlock Run Release` workflows actually produce and ship a `linux-arm64` (and `linux-x64`, if that architecture is ever deployed) `landlock-run` binary that lands in the built image** — this validation pass proves the mechanism is correct once the binary exists, not that the binary reliably exists in every build today.
- Landlock's grant list has no per-entry "optional" primitive analogous to bwrap's `--ro-bind-try`; this package filters the optional system paths with `existsSync` before building the grant list instead.
