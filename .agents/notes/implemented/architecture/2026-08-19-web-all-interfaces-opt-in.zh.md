# Agent Note: `dsh web --allow-all-interfaces`——在仅限本地回环的默认行为之外提供显式放行选项

Status: implemented

[English](2026-08-19-web-all-interfaces-opt-in.md) | 中文

## 问题

`dsh --profile web` 此前无条件拒绝 `--host 0.0.0.0`:Web GUI 的 `/api` 接口本身没有登录机制(`dsh-client-connection` 中的 Host/Origin 防护针对 DNS 重绑定和跨站请求,而非身份验证——见 [`api-request-trust.ts`](../../../packages/client/connection/src/api-request-trust.ts)),因此任何能够连接该端口的客户端都能以该进程用户的身份获得完整的工具执行能力(shell、文件系统、子进程)。在裸机上绑定所有网卡等于把这一切开放给整个网络。而容器化部署(位于 nginx 之后,自带身份验证与网络隔离)是一种合理的例外情形,此前的 CLI 却无法表达这种例外——唯一的办法是直接删除该检查,这会同时悄悄移除其他所有调用场景下的保护。

## 决策

`--host 0.0.0.0` 默认仍然报错,与之前完全相同。必须在同一次调用中额外传入 `--allow-all-interfaces` 才能放行;不带该参数时,`--host 0.0.0.0` 的错误文本保持原样。该参数本身不提供任何保护——没有身份验证,也没有额外防护——它只是记录运维者已经在此进程之外自行部署了保护措施。`--help` 会同时说明这一组合,并注明该参数只是关闭检查,并不会填补安全缺口。

## 后果

运维者现在可以运行 `dsh --profile web --host 0.0.0.0 --allow-all-interfaces --trusted-host <公网权威>`,将 GUI 提供给容器网络上的反向代理,前提是该代理(或其前面的另一层)提供真正的身份验证——`--allow-all-interfaces` 并不提供。同一部署仍然需要 `--trusted-host` 才能通过 DNS 重绑定防护:该防护的默认 `trustedHosts` 为空,因此任何 `Host` 既非本地回环、也不在已声明权威列表中的请求都会被拒绝,与绑定的主机无关。默认调用方式(不带参数的 `dsh web`,或 `--host 127.0.0.1`)保持不变。`packages/bundle/web-app/tests/startup.spec.ts` 同时覆盖了未变的拒绝路径与新增的选择性放行路径。

## 备选方案

- **直接删除该检查**——为了迁就一种部署形态,重新引入该防护原本要阻止的普遍风险(开发者在本机运行 `dsh web` 时的误操作)。
- **将绑定主机改为完全自由的字符串(`z.string()`),不设任何参数**——会失去"默认即报错"的效果;日常本地调用中一次拼写错误或误粘贴的 `--host 0.0.0.0` 将不再报错,而是直接悄悄暴露端口。
- **以 `--trusted-host` 非空作为放行条件,而非专设参数**——混淆了两个独立事实(DNS 重绑定防护接受哪些 Host 头,与运维者是否已经接受"绑定所有网卡"的风险);某些部署可能出于无关原因配置了受信任主机,却并不打算绑定所有网卡。
